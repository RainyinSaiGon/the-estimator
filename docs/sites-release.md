# Sites application and GitHub releases

The public application stays at <https://the-estimator-anduin-vu.zanyloach6.chatgpt.site>. Its company workflow is `/company-workspace`. GitHub is the source of truth for the complete Sites source tree.

## Temporary public demo access

Sites builds enable `PUBLIC_DEMO_ACCESS=true` by default so reviewers can open `/company-workspace` without a ChatGPT sign-in. The flag can be overridden to `false` in the build environment to restore the sign-in gate. Public visitors use a dedicated shared demo actor that is separate from Site account IDs; existing account-owned workspaces and the earlier private-estimate APIs remain account-scoped.

The demo actor can create, edit, analyze, review, estimate, freeze, track and evaluate company requests. Its workspace is shared by every anonymous visitor: request text, settings, approved knowledge and uploaded files are visible to anyone opening the public demo. Every request owned by the shared demo actor is forced into the synthetic cohort, including requests from signed-in members and signed webhooks after `PUBLIC_DEMO_ACCESS` is disabled. These requests cannot enter recorded delivery training. The server still uses the configured OpenAI service for real analysis. Webhook and MCP credentials can be rotated or revoked in the shared demo; anyone visiting can change them, and the generated one-time values must never be used by a real company. Turn `PUBLIC_DEMO_ACCESS` off after judging or before entering any real customer material.

## Release path

The **Sites release artifact** GitHub Actions workflow runs for pull requests and pushes to `main`. It checks types, evaluation invariants, and the compiled Worker against isolated local D1/R2. It builds the deployed Sites application with `npm run build:sites` and uploads `sites-release-<commit>` with its GitHub commit and Git tree recorded in the archive. No production credential is available to CI.

After merging and successful CI, use the existing Sites source checkout and its short-lived source credential. Run `scripts/stage-sites-github-release.mjs <verified-main-sha>` from that clean checkout to stage the entire GitHub tree. Extract the matching Actions artifact there. The Sites source helper commits/pushes that tree and packages the checked build; save and publish it with the native Sites tools. Check deployment completion and `/release.json` against the merged GitHub commit. Do not copy individual application files between the repositories or rebuild a different revision.

Sites currently exposes public publication through its native tools, with short-lived source credentials. It does not provide this project a permanent public GitHub auto-deploy credential. CI build/artifact creation is automatic; final publication uses the Sites tool. This workflow does **not** claim unattended publication on every push.

The native Next.js/Go/Python/Postgres application in `apps/web` and `services` is a separate deployment target. Building a Sites archive does not deploy those processes. Existing D1 `projects` records remain intact alongside the company workflow tables.

## Live workflow

- Requests: one AI-only entry point into the company workflow with a focused list and full-page request detail. Analysis shows provisional work-package suggestions under its summary, including rationale and exact source quotes when verified; people can edit the task template, quantity, owner, completion criteria and dependencies before scope confirmation. The numeric estimator supplies per-task low/central/high effort after review; AI never generates hours. Frozen requests show their immutable commitment baseline alongside task statuses, assignees, planned dates, milestones, blockers and an append-only proposed scope-change log. These tracking fields do not change the frozen baseline. PDF selectable text is extracted with page references; image-only PDFs are flagged for OCR, which is not provided.
- Knowledge and settings: administrators can allow exact hostnames, fetch bounded public HTTPS HTML/text/Markdown/JSON as draft, inspect and approve each version, and re-fetch to create a new draft. Findings and MCP results show source URL, evidence, digest and retrieval date. The domain allowlist must contain trusted official sources; the Worker checks public DNS answers but cannot pin the resolved address during its outbound fetch. Configuration remains versioned and company-neutral across fields, priorities, products, capabilities and task priors. Company intake JSON Schema is available from Connectors.
- Members: stable Site account IDs with administrator, estimator, reviewer and viewer roles. A new member signs in, shares their Site account ID, and an administrator adds that ID. Email addresses are not authorization identifiers.
- Connectors: signed demo-form/CRM intake with event deduplication; read-only MCP tools for approved knowledge and the intake schema. Gmail polling is deferred in the Sites implementation.
- Estimation: configured task priors are adjusted by the median actual-to-estimate ratio from comparable, independently approved recorded training projects. A task needs at least three distinct projects; factors are bounded from 0.5× to 2×. Matching uses reviewed domain, request type, task template and complexity. Holdout, synthetic, self-reviewed, invalid and non-comparable outcomes are excluded. The estimate records its sample count and source baseline IDs. Staffing-based calendar dates are not provided because availability calendars are not configured.
- Delivery: original task actuals, separate added scope, evidence and a designated different reviewer. The API rejects self-review, stale versions and changes/deletion of frozen records. Rejected actuals remain in history. Task tracking updates use optimistic version checks and are stored separately from the frozen baseline digest.
- Review & results opens on its review queue with actionable links back to briefs, observed AI activity, source quotations and saved reviewer decisions. These are workflow counts, not accuracy or time-saving claims. Delivery results is a separate view with an evidence-collection guide when real outcomes are unavailable. Methodology and exports are available under its collapsed **Methodology & data export** section. The split remains fixed at baseline freeze using `sha256(the-estimator-delivery-holdout-v1:<record-id>)[0] % 5 == 0`; holdout is 20%. Recorded and synthetic cohorts stay separate. Recompute exported JSONL with `python evaluation/evaluate_delivery_holdout.py --records <private-export>`. Workspace switching, creation, AI connectivity and settings revision details live under Workspace settings → Company settings.

The training adjustment is a transparent descriptive factor, not a claim of improved accuracy. Holdout outcomes never tune estimates. A small recorded cohort cannot establish accuracy or improvement. Issues #38 and #39 still require real representative independently approved evidence.

## Webhook activation

An administrator configures the external form/CRM sender; access to Anduin's submission system is not assumed. Open Workspace settings → Integrations → Connectors and enable the webhook, then copy its one-time secret into the sender's secret store. JSON fields are `submissionId`, `title`, `text`, `cohort` (`recorded` or `synthetic`), and optional `attachments` with `name` and `contentBase64`. Public demo submissions are always recorded as synthetic, regardless of the supplied cohort. Use a stable event ID for retries; changed content under the same ID returns 409.

Sign the exact UTF-8 bytes `timestamp + "." + rawBody` with HMAC-SHA256. Headers are `X-Workflow-Timestamp` (RFC3339 UTC), `X-Workflow-Signature` (hex), and `Content-Type: application/json`. Timestamps expire after five minutes. Rotation/revocation invalidates old secrets. Accepted requests start analysis automatically; provider failures stay visible and can be retried from Requests.

Webhook payloads are bounded to 5 MB, ten files, 2 MB each and 4 MB combined. DOCX, XLSX, CSV, text and selectable-text PDF adapters run server-side; PDF pages retain references, and image-only PDFs are flagged as requiring OCR. A retry with the same event ID and payload retries a failed analysis on the original request. Changed content under the same ID remains a conflict. Incomplete sources must be reconciled and acknowledged before scope confirmation. OCR and legacy DOC/XLS are not provided.

## Secrets, data and limits

Production `OPENAI_API_KEY` and `WORKFLOW_ENCRYPTION_KEY` belong only in Sites secret settings. The encryption key is 32 random bytes encoded as Base64 and protects webhook credentials with AES-GCM and company-bound authenticated data. Do not rotate it on an existing database without migrating encrypted credentials. MCP tokens are shown once and stored as hashes. Only approved company knowledge is returned by the MCP tools; tokens cannot write data. Platform-managed connections use `/mcp`: call `company_list`, then supply `companyId` to knowledge tools. Custom clients may instead use the company-scoped URL in Connectors.

Outside public-demo mode, requests, originals and exports require an authorized organization identity. AI receives submitted text and extracted material only after explicit intake or a configured signed webhook. Private file keys are not public download URLs. Unfrozen requests and originals can be deleted from Requests. Frozen baselines, reviewed outcomes and audit history are retained; this prototype has no automatic retention purge. Private exports must stay outside Git. Limits are 50 owned organizations, 100 members, 200 requests and 200 knowledge versions per organization; latest 100 audit events are shown. Administrators must agree retention and deletion handling before storing customer data.

The existing account's OpenAI credential has a configured expiry; renew it in Sites secret settings before that expiry. A successful deployment does not prove a third-party form or MCP client is configured. An actual authorized client call verifies the connection; independent review requires a different real signed-in reviewer in production.
