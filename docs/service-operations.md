# Local service operations

The native Next.js web app and the Go and Python APIs each expose `GET /health/live` and `GET /health/ready`. Liveness reports that the process is serving HTTP. Readiness reports whether that service can accept work; the web readiness route also checks that both preview API health routes respond. Compose publishes only the web app on loopback and waits for readiness before starting it.

## Request logs

The preview and health routes in the web app, plus all Python and Go HTTP routes, write one JSON request event with a timestamp, severity, service, event name, request ID, method, path, status, and duration in milliseconds. The web app forwards its validated `X-Request-ID` to the two APIs. Services accept only UUID-shaped or 32-character hexadecimal IDs, replace other values, and return the accepted ID in the response header.

Request logs omit bodies, briefs, query strings, headers, cookies, and credentials. Do not add those fields to request events. Python and Go application startup and shutdown messages use the same JSON format.

## Timeouts

- The Next.js BFF has a 50-second total deadline across brief analysis and estimation. Set `PREVIEW_TIMEOUT_MS` from 100 to 60,000 milliseconds to change it. The longer default allows explicitly selected model-backed analysis to finish.
- Go defaults to an 8-second request deadline (`REQUEST_TIMEOUT`), with a maximum of 30 seconds, bounded header/body reads, response writes, a 60-second idle timeout, and a 10-second graceful shutdown.
- Python defaults to a 40-second ASGI request deadline (`REQUEST_TIMEOUT_SECONDS`, maximum 45), a 5-second keep-alive limit, and a 10-second graceful shutdown. The model client also has a finite request timeout.
- Invalid timeout values fail closed at service startup or return the BFF's generic service-unavailable response. Error messages never echo configured values.

## Configuration and credentials

Use each service `.env.example` as a reference for local process variables. Services consume process environment only and do not search for or load arbitrary env files. Next.js follows its documented local env-file behavior within `apps/web`. For local AI only, Docker Compose may read `OPENAI_API_KEY` from an explicitly selected ignored env file and inject it into the Python service at runtime. It is not mounted as a file, passed to the web service, or included in a build stage. Docker build stages must not receive credentials through `ARG`, `ENV`, or copied env files. The Docker ignore rules exclude local env files throughout the monorepo.

Sample mode and the Go estimator need no credentials. The optional local agent mode requires `OPENAI_API_KEY` and `AGENT_MODEL` in the Python service environment. It sends the submitted text and capability profile to OpenAI only when the user selects AI mode. The brief service requests deletion of the completed agent session; this is not a zero-retention guarantee. Do not use confidential client materials in this local preview. Hosted AI remains disabled, and the provider key is never read by browser code, logged, or committed.

No production host, routing, or persisted data is changed by this local Compose setup.

## Optional private records

See the [first-party identity threat model](identity-threat-model.md) for account-recovery behavior, security limits, key-handling gates, and local-preview restrictions.

The base Compose file leaves identity and private records disabled. To enable them, configure the first-party identity database password and BFF secret, plus the record database password, service-token secret, content-encryption key, and identity-index key in the ignored local env file. Run `compose.identity.yaml` and `compose.private-records.yaml` together with the base file. OIDC values are optional and are used only during an explicit migration of a previous provider-owned workspace; the legacy callback is not needed for first-party sign-in or record access.

The estimator Go service requires `DATABASE_URL`, `SERVICE_TOKEN_SECRET`, `CLIENT_CONTENT_KEY`, and `IDENTITY_INDEX_KEY` together. Use distinct random values. `SERVICE_TOKEN_SECRET`, `IDENTITY_BFF_SHARED_SECRET`, and all database passwords must be independent. The service/content/index keys must each be a base64 encoding of 32 random bytes; use separate URL-safe hex values for the PostgreSQL passwords. `IDENTITY_INDEX_KEY` stays stable for the lifetime of the account mapping; `CLIENT_CONTENT_KEY` stays stable for decrypting saved snapshots. `RECORD_RETENTION_DAYS` defaults to 90 and must be between 1 and 3650. The Go services apply their initial idempotent schemas at startup only after their settings validate and PostgreSQL is reachable.

First-party record ownership uses an HMAC of the identity authority and stable account UUID. Raw account IDs, email, and title are not stored as plaintext in the records database. The Next.js BFF resolves the HttpOnly session through the identity service and forwards only a short-lived HS256 service token with an audience, random token ID, key ID, and operation-specific scope (`private-records:read`, `:create`, `:update`, `:delete`, or `:migrate`). Go validates its algorithm, signature, key ID, required scope, issuer, audience, account UUID, issue time, and expiry before every private-record operation. An owner may rename a saved record; this updates the separately encrypted title and matching snapshot title only. The reviewed brief, scope, estimate, and evidence remain frozen. The active key ID and secret must match between the BFF and Go service. Keep prior key IDs and their exact secret values in `SERVICE_TOKEN_VERIFICATION_KEYS` on Go while tokens signed before rotation may still be in flight. To rotate, deploy a new active key ID/secret to the BFF while Go accepts both old and new IDs, then remove the old Go verification key after at least two minutes. Preserve the `legacy` key ID during the first rotation so previously issued unlabelled tokens remain valid for their short lifetime. Never place these settings in browser-visible variables. The database stores only an internal random account UUID, pseudonymous owner index, random record UUID, schema version, timestamps, nonce, and ciphertext. The full snapshot (including title, uploaded original file bytes when present, and extracted client source) is encrypted using AES-256-GCM with account and record identifiers as additional authenticated data. Titles have a separate encrypted column so listing records does not decrypt whole uploaded files. Version 1 reserves a null delivery outcome for later delivery-history work. Go alone receives PostgreSQL and content-encryption settings; Python remains stateless.

Legacy workspace migration requires active first-party and legacy OIDC sessions. The BFF sends a 60-second service token that carries both verified identities only for the dedicated migration endpoint and the `private-records:migrate` scope. Go changes the HMAC owner mapping and, if both workspaces exist, decrypts and re-encrypts each record with the destination account UUID as authenticated data in the same database transaction. It never links identities by email. Keep the OIDC callback and secrets until the owner has confirmed the migrated records.

Expired records are excluded from reads immediately. A six-hour cleanup removes expired ciphertext and then removes account-index rows that no longer own records. Individual deletion and whole-workspace deletion are owner-scoped. Request logs contain only route, request ID, timing, and response status; never add source text, titles, session cookies, tokens, or credentials to logs.

The identity service stores sign-in attempt limits in its own PostgreSQL database using a keyed pseudonymous email identifier. Limits therefore survive restarts and are shared across identity replicas; they are account-level controls only. Public deployments still require edge/IP and registration limits plus abuse monitoring. Session renewal replaces the prior opaque token and cannot extend a sign-in beyond its 30-day absolute lifetime; existing sessions are capped at their original expiry during migration. First-party private workspaces remain an opt-in local preview. Verify account isolation with two separate local accounts. Production deployment, email verification/recovery, MFA, Sites identity linking, D1 import, and traffic cutover remain separate gates.
